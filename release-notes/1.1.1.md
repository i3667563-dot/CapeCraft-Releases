## CapeCraft 1.1.1

Кастомные анимированные плащи для Minecraft 1.21.1 / 1.21.4 / 1.21.8 / 1.21.10 / 1.21.11 / 26.2

### Установка

1. Установи [Fabric Loader](https://fabricmc.net/) для своей версии Minecraft
2. Скопируй нужный `capecraft-1.1.1-<версия>.jar` в папку `mods`
3. Запусти игру

### Поддерживаемые форматы

PNG • Stacked PNG • APNG • GIF • WebP (lossless)

### Конфигурация

`config/capecraft.kn` — создаётся автоматически при первом запуске.
Полный список ключей и разбор настроек — в
[README](https://github.com/i3667563-dot/CapeCraft-Releases/blob/main/README.md).

### Что нового

**Чужой игрок без объявления больше не остаётся без плаща.** В 1.1.0 игрок,
который не участвует в цепочке синхронизации, получал на экране ровно ничего:
мод его видел, показывать ему было нечего. При этом плащи адресуются по
`{username}` и `{uuid}`, то есть плащ зарегистрированного у твоего провайдера
человека находится тем же запросом, что и любой другой. Теперь такому объекту
мод даёт 5 секунд на объявление, а по истечении срока навязывает свой локальный
набор.

Правило ровно такое:

- **объявился** — показываем его набор, с его `when` и приоритетами;
- **не объявился за 5 секунд** — показываем мой набор;
- **пришло объявление позже** — оно перебивает навязанный набор.

Секрет на то, что 5 секунд: игрок может зайти на сервер чуть позже остальных
или объявиться уже после первого снимка роустера. Раньше такой срыв не
лечился ничем — набор не появлялся до перезахода.

**Важная тонкость, найденная на живых двух клиентах.** Объявляет пустоту игрок
**без провайдеров** — сообщение об объявлении шлётся всегда, даже когда набор
пуст. Если считать это объявлением, то игрок без конфига остаётся без плаща
навсегда, а пятисекундный срок ожидания не срабатывает вовсе: «молчания» не
было, объявление было. Теперь пустое объявление означает «набора нет» и даёт
локальный набор сразу, без ожидания.

Проверено на стенде из трёх машин: сервер, `GGSHNIKK` с провайдером
`https://skins.ggshnikk.online/api/animated/v1/skins/{username}/cape.json` и
`Eonixx` вообще без провайдеров. До правки плащ `Eonixx` не показывался
`GGSHNIKK` вообще, хотя оба аккаунта были зарегистрированы на этом провайдере
и ответ по нику отдавал картинку. После правки видны оба.

Чтобы увидеть плащ чужого игрока, у которого нет своего набора, у наблюдателя
должен быть свой провайдер — навязывается именно его набор, и `{username}`
подставляется ник **того, на кого смотришь**. Обратное тоже верно: чтобы
увидеть чужой набор с чужим `url`, у наблюдателя должен быть включён
`allowForeignUrls` (по умолчанию выключен).

### Исправлено

- **Свой `file`-плащ не терялся на входе на сервер.** Сервер рассылает снимок
  роустера всем, включая объявившего, а локальный файл по умолчанию наружу не
  уезжает (`shareLocalProviders = false`) — в своём же снимке его нет. Раньше
  «свой» набор брался из роустера, и локальный плащ исчезал ровно в момент
  входа на сервер. Теперь свой набор берётся из локального конфига всегда.
- **`/cp reload` пересчитывает и навязанные наборы.** Он перезагружал только
  мой собственный плащ, потому что чужие объекты «живут по объявленным ими
  наборам». Для навязанных это неверно: они держатся на моём конфиге, и его
  смена обязана их обновлять. Объявленные наборы по-прежнему не трогаются.
  В `/cp status` видно, сколько объектов сейчас держится на навязанном наборе.
- **Плащи и GPU-текстуры молчащих игроков не переживают выход с сервера.** На
  `DISCONNECT` чистился цикл по списку объявившихся, а плащи остальных
  оставались в кэше и показывались на следующем сервере вместе с чужим набором
  провайдеров. Заодно сбрасывался свой id: при выключенной синхронизации он в
  этот список не попадал вовсе и уезжал на следующий сервер.
- **Больше не планируется загрузка без провайдеров.** На каждом кадре рендера в
  фоновую задачу уходил запрос при пустом наборе — все пять секунд ожидания
  объявления, с ошибкой «нет провайдеров» в `/cp list` и событием
  `ProviderNotFound` на каждый кадр. Теперь пустой набор выходит сразу.

### Внутри

Мод не изменился, но стала возможна следующая работа над редактором
конфигурации: разбор конфига вынесен в общий код без MC API, схема ключей
(`ConfigSchema`, `WhenSchema`) стала единственным источником истины, а
ошибки в логах и в разборе теперь указывают точное место в файле. Ничего из
этого ещё не подключено к редактору — сам плагин и LSP будут следующим шагом.

### Проверено

- Шесть версий: 727 тестов на версию, 4362 суммарно, 0 failures.
- Все примеры конфигов из README компилируются тестом: приём в сплошных
  блоках не пропускает опечатку, и документация не может разъехаться с кодом.
- Правило выбора набора проверено на пяти случаях (свой, объявился, объявил
  пустоту, ждём, навязан) и на том, что пришедшее позже объявление перебивает
  навязанный набор. Проверка мутациями: обмен ветвей роняет четыре теста,
  снятие ветки пустого объявления — тест на «не ждёт пяти секунд», смена
  сравнения на границе срока — семь тестов.
- **Живой прогон на трёх точках входа.** Dedicated-сервер плюс два настоящих
  клиента, у одного web-провайдер, у другого провайдеров нет вовсе. Именно он
  нашёл поведение с пустым объявлением, и именно на нём правка подтверждена:
  видны оба плаща. Правка целиком в выборе источника; в 1.1.0 такой прогон уже
  был (см. заметки 1.1.0).
